# evals/test-prompts.md — Тестовые запросы для проверки роутинга

> Цель: под каждый скилл — минимум один реальный запрос, который должен триггерить
> именно его (и явно НЕ триггерить соседние домены, если это важно проверить).
> Формат и обязательность — `CONTRIBUTING.md` шаг 7 («Добавить новый скилл»),
> `SCHEMA.md` раздел 8 (чеклист готовности скилла).
>
> **Как проверять:** прогнать запрос через `ROUTER.md` (таблица триггеров + алгоритм
> по шагам) и свериться, что домен(ы) в колонке «Ожидается» совпадают с тем, что
> реально загрузит роутер. При изменении `description` в frontmatter скилла —
> перепрогнать связанные строки.

## `product-design`

| Запрос | Ожидается | Комментарий |
|---|---|---|
| «ПМ дал задачу поправить график работы сотрудников, но неясно: можно ли выбрать сразу нескольких сотрудников и изменить у всех график на день, можно ли выбрать несколько дней сразу, можно ли трогать прошедшую дату» | `product-design` | Проверяет триггер «требования» / размытое ТЗ — скилл должен вести к уточняющим вопросам (Метод, шаг 1), а не к готовому решению. |
| «Какой должен быть user flow для оформления отпуска сотрудником, если у HR-админа и сотрудника разные шаги согласования?» | `product-design` (+ `frameworks/jtbd.md` при нескольких ролях) | Проверяет триггер «user flow» + нелинейный сценарий (принцип №5, обязателен flow chart) + разбор по ролям. |
| «Спроектировать фичу уведомлений на основе результатов ресёрча по онбордингу» | `ux-research` → `product-design` → `design-systems` | Проверяет цепочку из `ROUTER.md`: скилл не подменяет ресёрч, подключается после него, и передаёт эстафету в design-systems на компонентном уровне. |
| «Собери спеку компонента Date picker — какой вариант лучше» | `design-systems` (не `product-design`) | Негативный кейс: запрос уже на уровне компонента, а не флоу/фичи — должен уйти в design-systems, не сюда. |

**Статус проверки:** сверено вручную с таблицей триггеров `ROUTER.md` и `description` в `skills/product-design/SKILL.md` — формулировки запросов пересекаются с триггерными словами домена (флоу, user flow, требования, фича, сценарий), негативный кейс (компонент) явно выведен в `design-systems`. Прогон через реальный роутер в отдельной сессии Zhandos — не выполнялся.
