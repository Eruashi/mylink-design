# Гайдлайн компонента

## Когда использовать
- «Напиши гайдлайн для Modal header»
- «Переведи гайдлайн Button из чек-листа в новый формат»
- «Задокументируй компонент по формату Sidebar»

Скилл не покрывает: изменение самого компонента, миграцию токенов (→ `ds-token-update`), решения по API (→ `skills/design-systems`).

## Что делает
Собирает гайдлайн по `templates/component-guideline.md` (10 разделов: суть → дизайн → в интерфейсе → разработка web/Flutter; `docs/guideline-structure.md`) из фактов компонента в Figma и данных `ds/`. Факты (анатомия, размеры, свойства, состояния, токены) — только из источников; правила использования — формулирует сам и помечает `TODO: проверить` там, где это не следует из данных. Результат — `ds/guidelines/<компонент>.md`.

## Контекст и принципы
- **Факт или предположение — видно всегда.** Всё, что не прочитано из Figma или `ds/`, помечено `TODO: проверить` или «уточнить у [кого]». Выдуманное правило хуже пустой секции.
- Имена компонентов, свойств, значений — латиницей как в Figma; токены — полным именем из `ds/tokens.md` со значением.
- Не на токене — так и пишем: «нет токена» (не подставляем похожий).
- Раздел не относится к компоненту — не выводим. «Flutter» — только для кроссплатформенных и мобильных компонентов.
- Показывать, а не рассказывать: в «Свойствах», «Состояниях», «Поведении», «Делаем / не делаем» — ряды примеров; таблицы — в «Спецификации» и «Flutter».
- Спецификация полная: фронты читают гайд и компонент, Dev Mode есть не у всех.
- Flutter-имена и Mantine-пропсы неизвестны → `TODO: мобильщики` / `TODO: фронты`, не угадываем.
- Тон — короткие утверждения, прямые запреты, числа без px.
- Figma — только чтение, пока пользователь не попросил вёрстку и не назвал ветку.

## Метод
1. **Контекст.** Найди компонент в `ds/components.md` (node, страница, статус, % Tokens, старый гайдлайн) и `ds/component-props.md`. Grep имени по `figma-status/**`, `tasks/`, `ds/decisions.md`. Есть старый гайдлайн (чек-лист, MoSCoW) — прочитай его как источник требований.
2. **Факты из Figma** (`use_figma`, только чтение):
   - структура слоёв типичного варианта → «Анатомия» (3); строение ключевого вложенного компонента (напр. Counter-badge: радиус, текстовый стиль, отступы, цвета по состояниям) — мини-блоком в «Анатомии»;
   - пара «группа + элемент» (Tabs / Tab): «Свойства» и «Спецификация» — двумя подблоками «группа» и «элемент»; «Состояния» — по элементу;
   - `componentPropertyDefinitions` → «Свойства» (4); свойство, которое не действует при другом значении, — «не действует при …»;
   - оси State (у компонента или вложенного) → «Состояния» (5); по каждому состоянию сверить **вес шрифта** (Regular / Medium), цвета текста, иконки и варианты вложенных компонентов — они часто меняются вместе с состоянием;
   - реальные макеты с компонентом (инстансы на страницах продуктов) → «В интерфейсе» (8): собрать пример из инстанса целого компонента (группы), не из отдельных элементов;
   - размеры, паддинги, зазоры, радиусы, текст по размерам и состояниям → «Спецификация» (8); токены — `ds/_scripts/component-token-audit.js`, для гайдлайна достаточно `MODE='summary'` + findings классов `old*`/`raw`;
   - где компонент используется — `getInstancesAsync()` у каждого варианта → «Когда использовать» (2);
   - на странице компонента уже есть свободный гайд (фрейм с текстом рядом с компонентом) — прочитай и учти, даже если в реестре «нет»;
   - скриншот типичного варианта — для понимания.
3. **Сборка** по шаблону. Для каждой секции: сначала факты, затем правила. Правило без источника → `TODO: проверить`.
4. **Проверка перед выдачей:**
   - каждое имя свойства и значения есть в `ds/component-props.md`;
   - каждый токен есть в `ds/tokens.md`;
   - число вариантов совпадает с Figma;
   - строка покрытия — в чат и в status-файл: «Разделов N из применимых M, на фактах K, TODO: T». Раздел «на фактах» — если всё, кроме TODO, взято из Figma или `ds/`.
   - при переписывании гайда — число TODO до и после, ни один не потерян;
   - утверждения старого гайда, которые не совпали с компонентом, — списком в status-файл («в старом гайде неверно: …»).
5. **Выдача:** файл `ds/guidelines/<компонент>.md` + короткий ответ по «Формату ответа»: вывод, список TODO для пользователя (до 5 главных), следующий шаг.
6. **Вёрстка в Figma** — только по просьбе и в названной ветке. Образец — Modal header v2 `23637:1666`:
   - фрейм 1600, поля 96, между разделами 160; обложка — синяя с превью компонента (клон обложки образца);
   - раздел — две колонки: слева 320 (номер, заголовок 32/40 Bold, одна серая строка 16/24 и, если есть, одно «почему» 14/20 — зачем так устроено: «Filled — это segmented control, Inline — навигация по разделам»), справа примеры на подложке `bg/neutral/primary`, радиус 24, паддинг 48; подписи **над** примерами 13/18 серые, везде одинаково;
   - плотность: на канвасе ≤ 600 слов; «Спецификация» ≤ 3 таблиц по ≤ 12 строк (вариации — колонками: размеры, стили); всё остальное — в md;
   - «Свойства»: размеры — одной картинкой-линейкой (элементы всех размеров рядом, для группы и элемента друг под другом);
   - примеры с `Inverted=No` / белым фоном — на белых плитках внутри серой подложки;
   - максимум одна нейтральная плашка на гайд — только для критичного риска (a11y, конфликт с DS), 1–2 строки;
   - «Свойства» — сетками: варианты (3–4 в ряд) и переключатели (только значение не по умолчанию), не ряд на каждое свойство;
   - «Когда использовать» и «Делаем / не делаем» — пары карточек с зелёной / красной линией сверху 3px; в «Когда использовать» только текст;
   - «Спецификация» — таблицы без заливки, линии `border/neutral/secondary`, шапка 12 medium серая, строки 14, высота 48; размеры — колонками одной таблицы (lg / md);
   - никакого оранжевого текста и TODO на канвасе; дефекты компонента не показывать как норму — только парой в «Поведении»;
   - Close button и мелкие компоненты — в масштабе 1×; не масштабировать (ломает привязки токенов);
   - `createAutoLayout` даёт белую заливку — сразу `fills = []`; вызов `use_figma` обрывается через ~60 с — не больше одной подложки за вызов; после таймаута проверить auto-layout (дети на y=0 → переключить `layoutMode`);
   - новая секция — справа от соседних с зазором ≥ 400, проверить bounds всех детей страницы; в SLOT инстанса можно добавлять элементы через clone + appendChild;
   - после — скриншоты всего фрейма и разделов, один проход правок; открытые вопросы и сделанное — в `figma-status/<файл>/<компонент>.md`.
7. **Фидбек.** Правки пользователя по гайдлайну → запись в `feedback.md` рядом.

## Формат вывода
Файл по `templates/component-guideline.md`. В начале файла одна строка-мета: `Источник: Core kit `<node>` (main), <дата>. Скилл ds-guideline <версия>. Черновик — перенести в Figma после ревью.` В чат — только сводка и TODO.

## Анти-паттерны
- Придумать сценарии «когда использовать» и выдать как решение команды.
- Описать свойство, которого нет в компоненте, или пропустить существующее.
- Голые числа и hex, когда есть токен; токен, которого нет в `ds/tokens.md`.
- Описывать словами то, что можно показать рядом примеров.
- Выводить раздел «Flutter» для web-only компонента или пустые разделы «Не применимо».
- Писать гайдлайн в Figma без явной просьбы и ветки.

## Примеры
✅ «Высота — 56, нет токена. Паддинг по горизонтали — `Spacing/spacing-6x-xll` (24).»
✅ «Когда не использовать: заголовок страницы — это `Header`. `TODO: проверить` — вывод по инстансам, правила в команде нет.»
❌ «Используйте Modal header во всех модалках» — не проверено, правила нет.
